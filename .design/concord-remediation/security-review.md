# Concord remediation security review

**Review target:** uncommitted working tree based on `cff0df246b91461f959d8dbe9154ba50bba2331c`, reviewed 2026-09-06 after the implementation freeze. This is a read-only source review except for this report. Evidence records were used to select boundaries, not as a substitute for inspecting the implementation.

**Verdict:** **pass with residual qualification and dependency risks**. The one verified medium-severity authentication defect found in the frozen review was corrected and independently re-reviewed in source; its focused real-HTTP/live-WebSocket regression passes with default and all features. I found no remaining verified critical, high, medium, or low security defect in the reviewed tree. The external-provider and dedicated-host qualifications listed under Review limits remain release evidence gaps rather than verified source defects.

## Resolved verified defect

### SR-01 — Medium — Resolved — Logout reported success when durable credential revocation failed

**Original location:** `concord/server/src/web/oauth.rs:811-829` in the reviewed freeze, specifically the discarded revocation result at former line 815. **Corrected locations:** `concord/server/src/web/oauth.rs:813-854`, `concord/server/src/web/router.rs:90-92`, and `concord/server/tests/session_authority.rs:1192-1303`.

**Original trigger and impact:** `POST /api/auth/logout` authenticated the session cookie and called `revoke_credential`, but discarded every revocation error and always returned a redirect that deleted the browser cookie. If SQLite was unavailable, busy beyond the operation's handling, or rejected the revocation write, the user observed a successful logout while the authoritative `auth_credentials` row remained active. A copied cookie remained usable, and an already connected WebSocket retained access because no successful revocation cancellation was emitted. This violated G01/R01's durable logout and restart semantics and created a security-significant false assurance at exactly the point a user was trying to terminate a credential.

**Resolution:** logout now clears an absent, invalid, expired, revoked, disabled, or cryptographically invalid cookie; authentication authority failures return `503` without `Set-Cookie`. A valid actor's revocation commits before success and live-credential cancellation. The idempotent concurrent/already-revoked path also cancels any residual live lease. Logout now has its own source-address auth rate limiter, allowing its handler to classify an invalid/revoked cookie rather than having general API principal middleware intercept it. The route remains a same-origin cookie action under the exact-origin CORS policy and SameSite cookie boundary.

The regression injects an SQLite trigger that rejects the revocation update and proves `503`, no cookie clearing, no durable state change, continued cookie validity, and a still-live WebSocket. After removing the trigger it proves durable revocation, invalid cookie authentication, WebSocket closure, engine-session cleanup, and safe repeated logout of the revoked cookie. Saved evidence in `evidence/security-review/20260906T-sr01/` records default-feature `1 passed`, all-feature `1 passed`, and the existing browser failure-warning test `1 passed`; the two Rust log SHA-256 values are `d32eafbc4f0991c2df4ad623c8a494a35bb3d28aa3f5d4121707c838c5995709` and `988a64000c51b8cd2ad98589d9d0e611ecca764176ac404978dcc22e581e42fb`.

## Surface review

### Authentication, sessions, grants, and adapters

The durable `auth_credentials` row is authoritative for web, IRC, and bot actors; token kind, subject, expiry, revocation, version, disabled-account state, and transport scope are revalidated. REST's principal extraction, WebSocket's exact configured Origin check and per-command validation, and IRC's actor-bound connection state converge on this authority. OAuth access and refresh tokens are stored as hashes; code consumption and refresh rotation occur in write transactions, refresh reuse revokes the family and grant, and server-bound grants recheck membership and bans. Bot actions intersect credential scopes, installation grants, and domain permissions. No additional authorization bypass was verified.

The corrected SR-01 path now preserves the durable-revocation invariant when its write fails.

### Resource authorization, private projections, races, and replay

Channel and conversation authorization loads resource ownership from the database, denies nonmembers/banned users before role evaluation, enforces private-channel grants and private-thread parent/member constraints, and checks caller-supplied server/channel relationships. Message send/edit/delete/reaction/read operations authorize within admitted transactions and validate replies and attachments against the target conversation. Search builds its result set from authorized channel IDs inside the transaction and binds continuation state to policy versions. History, pins, bookmarks, thread/forum projections, presence, media metadata, event replay, and snapshot reconstruction use current resource state; deleted content omits protected payload fields. Authorization stamps are rechecked before adapter serialization, while queued delivery retains guards that revalidate current credentials and policy. I found no verified stale-grant or cross-conversation disclosure in these paths.

The implementation necessarily cannot retract bytes already written before a revocation commits. Its stated boundary is correct: subsequent enqueue/serialization decisions are fenced by credential and authorization versions.

### Media, uploads, and filesystem paths

Uploads are byte bounded at both Axum framing and streaming storage layers, admitted through bounded concurrency/quota controls, staged under server-generated IDs, fsynced, and claimed transactionally. Download and deletion go through actor-scoped media authorization. Storage keys are validated as relative normal components, and `cap-std` rooted opens/removes/renames prevent symlink traversal outside the media root. Response filenames strip header-active characters and unsafe content types are forced to attachment disposition. Legacy external imports use controlled streaming egress and retain their prior-public status. No path traversal, bearer-ID media access, or automatic external publication defect was verified.

### Egress, SSRF, providers, redirects, and body limits

`ControlledHttpClient` requires HTTPS/443 for general Internet destinations, rejects URL credentials and literal non-public IPs, supplies a custom resolver that rejects the entire DNS answer set if any address is non-public, disables ambient proxies, and re-runs destination validation for every redirect. Credential-bearing requests are restricted to their exact origin and cannot redirect. Response bodies and concurrency are bounded, including chunked responses. Operator-only scoped origins intentionally use system DNS so configured private administrative endpoints can work; this is an operator trust boundary rather than user-controlled SSRF. Webhook delivery performs a database grant/resource preflight after admission and immediately before the request. AT provider discovery constrains credential endpoints to the verified issuer origin and rejects credential redirects. No verified SSRF, DNS-rebinding, redirect credential leak, or unbounded provider response was found.

The `browser-fixtures` feature permits a loopback fixture resolver only when an explicit environment variable is set; the runtime also rejects non-loopback fixture addresses. Production packaging must continue to omit this feature. Qualification builds that enable it should be treated as qualification artifacts, not deployable release binaries.

### Secrets and external integrity

External credentials, pending AT OAuth state, AT signing keys, and outgoing-webhook signing secrets use XChaCha20-Poly1305 with random nonces and context-bound associated data. The key is stored outside SQLite, identified by a digest-derived key ID, and configuration rejects group/world-readable key and JWT files. Rotation uses compare-and-set updates in one immediate transaction and has explicit durable phases. Incoming webhook tokens and bot/IRC secrets are one-time plaintext values with indexed IDs and Argon2 hashes at rest. Outgoing webhooks sign timestamp plus exact payload, recheck the grant before transport, and fence lease completion. AT publication uses durable jobs, resource/grant versions, and reconciliation states. Interaction responses bind application, bot, channel, expiry, and one-use state. No plaintext-secret persistence, signature-confusion, or replay acceptance defect was verified.

### Operator migration, backup/restore, startup, and deployment

Migration history is checksum tracked and schema upgrades run under an exclusive maintenance boundary. Backup inventories reject symlinks/special entries, use private destination permissions and hashes, and reject overlapping source/destination paths. Restore validates manifest-relative paths, stages with exclusive private files, changes database and operation generations, revokes web sessions, pauses external jobs, verifies integrity and activated hashes, and refuses service startup while activation is incomplete. Configuration rejects sample/short secrets, unsafe production origins, insecure secret-file modes, incomplete TLS configuration, and missing storage. Required listeners bind before readiness is advertised and supervised task failures drive shutdown. No verified traversal, restore credential resurrection, generation-fence bypass, or production fallback to an in-memory authority was found.

### Qualification scripts and fixture seams

Browser/load seed binaries require `browser-fixtures`; storage fault hooks require their separate feature. Qualification scripts create credentials in isolated fixture roots, apply restrictive file modes, pass secrets through environment or private inventory files, and emit redacted credential counts rather than tokens to evidence. I found no command construction that incorporates untrusted remote data into a shell evaluation. The scripts do place credentials in child-process environments, which is acceptable for isolated qualification hosts but requires those hosts and evidence directories to remain private and be destroyed or revoked after use.

### Dependency status

`concord/docs/dependency-audit.md` accurately does **not** claim a green audit. The saved current audit JSON (`evidence/dependency-audit/20260906-schema32/after.json`) reports exactly three vulnerability matches: `RUSTSEC-2026-0118` and `RUSTSEC-2026-0119` for `hickory-proto`, plus `RUSTSEC-2023-0071` for optional `rsa`. The implicated Hickory DNSSEC/runtime resolver path is not instantiated, and the RSA package has no path from a Concord target. `RUSTSEC-2026-0253` for `lru` is separately classified by cargo-audit as an **unsound warning**, not one of the three vulnerability matches; its affected storage implementation is not instantiated. The `core2` maintenance warning and yanked `spin` version also remain. I found no blanket ignore or warning suppression. This is a residual supply-chain risk that must be re-evaluated on every AT Protocol/SQLx parent update; it is not a demonstrated reachable vulnerability in this tree.

## Review limits and remaining qualification

I inspected the design (G01-G24/F01-F26), implementation ledger, integration findings, dependency record and saved audit JSON, migrations, manifests, changed/untracked Rust sources, router and adapter boundaries, browser fixture gates, operator code, and qualification scripts. I did not independently run Cargo commands because the parent reviewer held the shared target for frozen final validation. I inspected the saved SR-01 default/all-feature and browser regression logs and verified their reported hashes. The parent validation, including its final-source IRC client and storage xSync/crash suites, is the source of the remaining execution evidence for this exact freeze; those checks were not executed independently by this reviewer.

The dedicated separate-host four-vCPU/eight-GiB one-hour workload has not been completed. Actual external AT provider behavior, real outgoing webhook receivers beyond controlled fixtures, reverse-proxy/TLS deployment, physical power-loss durability, and cross-platform filesystem semantics remain external qualification items. The parent is separately executing the available actual irssi/WeeChat client qualifier and storage xSync/process-crash suite on final source; this review does not pre-classify their results as globally unverified. The remaining external limits prevent a claim of complete release qualification despite resolution of SR-01.

## Post-review correctness-fix security addendum

After the initial security verdict, the parent correctness review corrected local avatar rendering and qualification behavior in `web/src/utils/externalUrl.ts`, `web/src/components/ExternalImage.tsx`, the two browser suites, `scripts/run-irc-client-qualification.sh`, and `server/src/bin/load_qualification_seed.rs`. I reviewed only this narrow post-review change for security and privacy regression. The verdict remains **pass with residual qualification and dependency risks**; I found no new security or privacy defect.

`safeSameOriginUploadUrl` accepts only an absolute-path reference of exactly `/api/uploads/` plus a lowercase, canonically hyphenated UUID. It rejects arbitrary relative routes, suffixes, query/fragment additions, protocol-relative URLs, schemes, hosts, traversal components, and malformed IDs. Because the returned value begins with one slash, the browser resolves it against the current origin; it cannot select another host. `ExternalImage` loads this narrow local form directly with `referrerPolicy="no-referrer"`, while all other values still pass through the HTTPS/private-host filter and require an explicit user action before third-party loading. The upload endpoint remains authenticated and applies live media authorization, so learning or rendering an attachment UUID does not make the ID a bearer capability. The browser regression covers canonical local rendering and blocks `/admin`, protocol-relative, loopback HTTPS, `javascript:`, and malformed-upload forms.

The authenticated restart test now observes one valid application `sync_snapshot` on each socket before restart, then requires each socket to close and receive a new valid `sync_snapshot` after restart before testing unreloaded message delivery and credential revocation. This uses Concord's actual protocol lifecycle rather than unrelated development-server diagnostics, strengthens timing evidence, and does not change production authorization or client state. The IRC qualifier binds the generated WeeChat token only in the client process environment and passes a literal environment reference to WeeChat, avoiding shell interpolation and command-line token disclosure; the disposable fixture directory is removed by the existing cleanup trap. Irssi's generated token-bearing config remains mode `0600`. The seed change to integer `div_ceil` is semantics-preserving and has no security effect.
